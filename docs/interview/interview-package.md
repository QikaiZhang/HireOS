## 1. 项目宣讲

### 30 秒版

> 我在做 HireOS，一个 AI 语音面试平台：候选人打开网页，AI 面试官语音提问、根据回答实时追问，最后生成评分报告。架构上是一套"媒体面 + 控制面"分离的系统——Go 写的媒体网关负责高并发音频流接入和中继，Python LangGraph 状态机负责面试流程和 LLM 推理，两者用 gRPC 双向流解耦。目前文字面试闭环和媒体网关的回声链路都已验证跑通。

### 2 分钟版（按"输入→状态→推理→输出→持久化"讲）

> 这个项目我想验证的核心命题是：**AI 面试这个产品形态成立，并且底层组件可以逐个升级而不推翻架构**。
>
> 第一阶段我先打通了产品闭环：Python Agent 用 LangGraph 状态机管理面试流程——预生成题库、逐题提问、每轮回答由 ReAct 式节点评估并决定"深挖追问/下一题/结束"，最后汇总评分报告，三个 HTTP 接口对外，会话状态由图中断点管理，报告落库可查，29 项端到端断言验证通过。
>
> 第二步是语音链路。这里我做了这个项目最重要的架构决策：把媒体接入独立成一个 Go 网关服务。原因有三个：一是规模——每路语音是 32KB/s 的持续字节流，Python 进程里叠 LLM 阻塞调用承载不了大规模并发；二是隔离——LLM 卡 2 秒时音频帧不能排队堆积，网关用有界缓冲加水位丢帧策略保证"宁丢不等"；三是演进——第二个月把 WebSocket 换成 RTMP 时，网关内部的 gRPC 契约和整个 Agent 层零改动。
>
> 网关目前的验证状态是：回声链路端到端跑通，按真实语音节奏（25 帧/秒）灌帧零丢帧，压力灌帧下丢帧守恒、缓冲有界。下一步是 Redis 会话路由、断线 seq 续传和压测验收门。

## 2. STAR-L 故事线

### 故事 A（主亮点）：媒体面/控制面分离的实时音频网关

| | 内容 |
|---|---|
| **S 场景** | AI 语音面试：每路音频 16kHz/16bit PCM = 32KB/s 持续流；目标支持数千路并发；LLM 推理存在 1~3 秒的长尾阻塞 |
| **T 任务** | 设计媒体接入层，保证大规模并发承载、LLM 阻塞不影响音频流、传输协议可替换（WS→RTMP） |
| **A 行动** | ① 独立 Go 网关：每连接读写双 goroutine，会话级双端有界缓冲（50 帧≈2s），80% 水位丢最旧帧，读泵永不阻塞；② 只搬字节不解码——codec 作字符串标签，热路径零解析，隐私内存即焚；③ 每房间一条 gRPC 双向流，worker 拨号接入，流生命周期=会话生命周期 |
| **R 结果** | verified：回声链路端到端跑通；25fps 真实节奏 100 帧零丢帧；500 帧压力灌入丢帧守恒（45+455=500）、缓冲有界不崩；200 帧真实服务冒烟逐帧一致 |
| **L 复盘** | ① 曾把"策略性丢帧"误判为"流控饥饿"，靠隔离实验证伪——实时系统的吞吐测试必须按真实节奏灌帧；② 修复了"worker 先于浏览器接入被误判重复"的时序 bug，教训是占用判定要用"端点认领"而非"对象存在"；③ 无界队列是我主动放弃的选项——实时音频的内存不可预期性比丢帧更危险 |

**三层追问准备**：

- **原理层**：为什么丢最旧不丢最新？→ 实时语音价值随时间衰减，ASR 要新鲜上下文；丢最新会"断在刚说的话"。水位为什么 80% 不是 100%？→ 保留突发吸收余量，实测稳态长度=水位线（有单测断言）。
- **工程层**：读泵被阻塞会怎样？→ TCP 反压传导到浏览器采集端，采集时钟漂移，丢帧从"可控策略"变"失控"；所以 Offer 全程非阻塞。慢消费者怎么处理？→ 下行写超时（5s）断开会话，计数上报。怎么知道丢了多少？→ `frames_dropped_total{reason}` 指标 + 守恒测试。
- **取舍层**：为什么不用现成的流媒体服务器（SRS/livego）？→ 它们解决的是"推流-拉流分发"，我需要的是"会话级字节中继 + 与面试业务的生命周期绑定"，自研核心只有几百行且有守恒测试兜底；成熟件是 Month 2 录制链路的候选。为什么不用 WebRTC？→ 服务端要 SFU/TURN/SDP，复杂度先于产品验证；WebRTC 留作客户端体验层的后续选项（架构文档既有决策）。规模扩大先失效在哪？→ PCM 带宽：10k 路 ≈ 2.6Gbps，解法是 Opus（省 80%，codec 字段已预留）。

### 故事 B：LangGraph 面试状态机与 human-in-the-loop

| | 内容 |
|---|---|
| **S 场景** | 面试是多轮动态流程：每轮回答质量决定"深挖/下一题/结束"，且进程重启不能丢流程定义 |
| **T 任务** | 把面试流程做成可测试、可恢复的状态机，通过 HTTP 对外提供 start/chat/report |
| **A 行动** | ① LangGraph StateGraph，节点返回增量更新，`interrupt_before=["listen"]` 实现人机中断，chat 接口 `update_state` 注入回答后恢复；② ReAct 评估节点输出结构化决策（深挖/推进/结束），深挖上限用代码硬约束不信模型；③ LLM 全链路 OpenAI 兼容协议 + 无 Key 时确定性 mock 兜底，兜底显式打日志 |
| **R 结果** | verified：29 项端到端断言（含异常路径 404/409）全部通过；无 Key 环境即可全量验证，配 Key 复用同一脚本验证真实推理 |
| **L 复盘** | ① 条件边改写漏了静态边导致图静默终结——LangGraph 节点无出边=隐式 END，不报错；② pydantic state 无注解字段不会成为图 channel，`room_id = ""` 这种写法是隐 bug；③ 报告 JSON schema 在 mock/LLM 间不一致，已列为接 MySQL 前必须固化的 P2 |

**三层追问**：

- 原理层：interrupt 机制本质是什么？→ checkpointer 存图状态，interrupt_before 标记节点前暂停，invoke(None) 从断点恢复——human-in-the-loop 是图运行时的原生能力而非业务补丁。
- 工程层：怎么防止 LLM 无限追问？→ 状态里 `deep_dive_count` 每题重置、代码侧硬上限 2 次，LLM 返回的 loop_ask 超限会被强制降级为 next_stage。会话怎么续？→ thread_id=room_id，MemorySaver 管断点；进程级 checkpointer 是已知限制，Redis checkpointer 在 Week 2 路线图上。
- 取舍层：为什么不用 Dify/开源 Agent 框架？→ 面试流程的控制流是核心业务逻辑，需要图结构可版本化、节点可单测、中断点可控；LangGraph 恰好提供这三样，而不是黑盒编排。

### 故事 C（方法论亮点）：一次"伪性能瓶颈"的定位

| | 内容 |
|---|---|
| **S 场景** | 网关冒烟：200 帧灌入只回 144 帧，下行掉到约 2 帧/秒，客户端超时 |
| **T 任务** | 定位是系统性阻塞还是测试方法问题 |
| **A 行动** | 现象像 gRPC 流控饥饿（~64KB 窗口量级）→ 做隔离实验：绕过 WS 层纯 gRPC 直灌 → 复现"恰好 40 帧停摆" → 调大窗口到 1MB → 依旧 40 帧，流控假设被证伪 → 重新读数发现 40 = 缓冲容量 50 × 水位 80% → 真相：瞬时灌 500 帧，水位丢帧策略在正确工作 |
| **R 结果** | verified：重写测试为 25fps 真实节奏后零丢帧 1:1 回收；压力守恒测试（45+455=500）成为回归资产 |
| **L 复盘** | 实时系统的吞吐异常先问"丢帧计数和缓冲长度"，再怀疑传输层；每次实验只证伪一个假设 |

## 3. 高频问题速答

| 问题 | 30 秒回答要点 |
|------|--------------|
| 端到端延迟多少？瓶颈在哪？ | 单轮 2~4.5s，60% 在 LLM，网关 <1ms（<0.1%）。所以网关的 SLO 是并发密度和丢帧率，不是延迟。 |
| 如何水平扩展？ | 网关无状态可多实例；会话路由在 Redis（planned），LB 不要求粘性——重连靠 seq 续传重挂；Agent 会话态换 Redis checkpointer（Week 2）。 |
| 为什么 gRPC 双向流而不是 HTTP？ | 两个方向都是持续消息流，轮询有延迟且表达不了"面试进行中"；流式让 LLM 逐 token 返回成为可能。 |
| 网关为什么自研不用 SRS？ | 我要的是会话级字节中继+业务生命周期绑定，不是流分发；核心几百行有守恒测试，成熟件留给录制链路。 |
| 数据一致性？ | 媒体面不落盘（无一致性问题的根源消除）；业务面报告落库与图状态分离，图状态重启丢失是已知 P2，Redis checkpointer 解决。 |
| 如果 LLM 挂了？ | 网关层：音频继续缓冲+水位丢弃，不会被拖死；业务层：报告生成的 LLM 调用失败降级 mock 报告并打日志（Phase 1 的兜底设计）。 |
| 做了哪些测试？ | relay 纯逻辑单测（水位/守恒/并发 race）、集成测试（bufconn 全链路+异常路径）、25fps 节奏吞吐测试、真实服务冒烟；混沌/压测验收门在 M3（planned）。 |
