# 音视频流基础 — 写给第一次接触音视频的工程师

> 本文是 [GATEWAY_SPEC](GATEWAY_SPEC.md) 的前置知识，结合本项目（HireOS 媒体网关）的真实参数讲解。
> 读完你应该能回答：一帧音频是什么、为什么 40ms、为什么"宁丢不等"、网关为什么只搬字节。

---

## 1. 声音是怎么变成字节的

人对声音的感知是空气振动（连续的模拟信号）。计算机要处理它，必须先**采样**：

```text
连续声波    ──采样──▶   一串数字
〜〜〜〜〜   每 1/16000 秒测一次压力值    [312, 298, 271, ...]
```

三个参数决定"数字声音"的规格：

| 参数 | 本项目取值 | 含义 |
|------|-----------|------|
| 采样率 | **16,000 Hz** | 每秒测 16000 次。16kHz 覆盖人声主要频段（电话音质），语音识别够用；CD 是 44.1kHz |
| 位深 | **16 bit** | 每次采样用一个 16 位整数记录（-32768 ~ 32767） |
| 声道 | **1（单声道）** | 语音面试不需要立体声 |

这个格式叫 **PCM**（脉冲编码调制）——采样后最原始、没有任何压缩的音频。命名 `pcm_s16le_16k_mono` 意思是：PCM、16 位、小端序（little-endian，字节的低位在前）、16kHz、单声道。网关的 `codec` 字段就是这串标签，网关自己**不理解**它，只是带给下游。

**算一笔账（本项目最重要的数字）**：

```text
16,000 次/秒 × 2 字节/次 × 1 声道 = 32,000 字节/秒 = 32 KB/s
```

每一路语音面试，上行就是 32KB/s 的持续字节流。1,000 路并发 = 32MB/s 持续灌入 —— 这就是"为什么媒体接入要单独一层"的物质基础。

## 2. "帧"是什么：为什么是 40ms

网络传输不能一次发一整个文件，也不能每采一个样本（16bit）就发一个包——那样包头开销比数据还大。实践中把一小段时间的音频攒成一批发送，这一批就叫**一帧**：

```text
40ms × 16kHz = 640 个采样点 × 2 字节 = 1280 字节/帧
每秒帧数 = 1000ms / 40ms = 25 帧/秒
```

帧长的权衡（这是所有实时音频系统都面对的取舍）：

| 帧长 | 优点 | 缺点 |
|------|------|------|
| 短（10~20ms） | 延迟低 | 包头开销占比大、每秒包数多（CPU/网络负担） |
| **40ms（本项目）** | 开销与延迟均衡，25 包/秒很轻松 | — |
| 长（100ms+） | 包效率高 | 端到端延迟明显，ASR 出字变慢 |

注意：**40ms 是链路延迟的下限之一**。你说的每个字，最少要在采集端攒 40ms 才能发出第一帧。实时系统里每一层都在为几十毫秒讨价还价。

## 3. 实时流的黄金法则：宁丢不等

这是网关设计的核心思想，和普通后端直觉**完全相反**。

普通后端（比如下单接口）：请求处理慢就排队，宁可慢不能丢——丢数据是事故。
实时音频：**过时的音频没有任何价值**。

想象面试场景：你说了句关键的话，此刻 ASR 正在处理，LLM 在思考（要 2~3 秒）。如果网关把你的语音帧排队等 LLM，等轮到处理时——你 3 秒前说的话早就说完了，延迟越积越多，最终候选人听到的是"回音式卡顿"，ASR 拿到的也是过时上下文。

所以网关的行为是：

```text
缓冲区（容量 50 帧 ≈ 2 秒）        水位线 80%（40 帧）
┌──────────────────────┬─░░░░░░░░┐
│  帧帧帧帧帧帧帧帧帧帧  │ ◀── 到达水位线就开始丢【最旧】的帧
└──────────────────────┴─────────┘
新帧从右进，旧帧从左被 worker 取走；取走速度 < 灌入速度 → 旧帧被挤出去
```

- 丢**最旧**：保住最新语音，ASR 永远拿到相对新鲜的上下文
- 丢帧计数上报（`gateway_frames_dropped_total{reason="watermark"}`）：丢可以，但必须**可观测**
- **读泵永不阻塞**：浏览器→网关的接收循环绝不能因为下游慢而卡住，否则 TCP 反压会让浏览器端采集漂移（丢帧从"策略"变成"失控"）

验证数据：集成测试里以 500 帧裸灌（远超消费速度），结果 45 帧送达 + 455 帧丢弃 = 500，守恒、不崩、不阻塞；按 25fps 真实节奏灌 100 帧，零丢帧 1:1 回收。这就是"策略性丢帧"与"失控丢帧"的区别。

## 4. WebSocket 上的音频长什么样

M1 的 WS 客户端协议极简（完整定义见 ws.go 顶部注释）：

```text
连接：ws://host/ws?room_id=demo-1&codec=pcm_s16le_16k_mono
上行：每 40ms 发一个二进制消息 = 1280 字节裸 PCM（不带任何头部！）
下行：二进制消息 = TTS 音频；文本消息 = JSON（字幕/会话结束通知）
```

一个重要设计点：**上行帧不带 seq/timestamp 头部**。因为：
- seq 由网关分配（每会话单调递增），网关是唯一有全局视角的组件
- timestamp 是网关收到时刻，用于统计转发延迟
- 客户端保持"纯字节流"，未来换 RTMP 时客户端逻辑与 seq 语义解耦

代价：网关分配 seq 意味着重连续传时网关必须知道客户端上次发到哪（M2 的 Redis 注册表解决）。

**为什么不用 MediaRecorder？** MediaRecorder 是浏览器现成的录音 API，但它输出 webm/opus **容器格式**——网关要解析容器才能取出裸音频，违背"网关不解码"原则。所以 M1 用 AudioWorklet（浏览器音频底层 API）直接拿 PCM 裸样本，攒 40ms 发一帧。Opus 压缩（省 80% 带宽）留给 Month 2 评估，`codec` 字段就是为那天预留的。

## 5. 为什么下游用 gRPC 双向流

网关 ↔ worker 之间是"双方向都是持续字节流"的对话：

```text
worker → 网关：TTS 音频块、字幕文本、结束指令
网关 → worker：音频帧（连续不断）、会话终止通知
```

HTTP 请求-响应模型表达不了"双向持续"的语义；gRPC bidi stream 一条连接两个方向各走各的，且帧有序、可靠。方向约定（容易绕晕，务必记住）：

- **worker 是 gRPC client**（它连进网关），发 `WorkerFrame`（TTS/文本/控制）
- **网关是 gRPC server**，发 `GatewayFrame`（上行音频/终止通知）

一个房间里 worker 与浏览器 WS 连接 1:1 绑定，流的生命周期 = 会话生命周期。

## 6. 延迟预算：每一毫秒去了哪

一次"候选人说话 → 听到 AI 回答"的完整旅程：

```text
你说的话
  ↓ 攒 40ms 成帧                    ┐
  ↓ 网络上行                         │ ~50ms
  ↓ 网关转发 < 1ms                  ┘
  ↓ ASR 识别（流式，边说边识别）       200~800ms   ┐
  ↓ ASR 检测你说完了（VAD/句尾）       +静音检测    │
  ↓ Agent：LLM 生成追问               1~3 秒      │ ~2~4.5s
  ↓ TTS 合成首个音频字节               200~500ms   │
  ↓ 网关下行 + 浏览器播放              ~50ms      ┘
```

网关的角色是**不增加可感知延迟**（<1ms），并保证中间任何一环卡住（LLM 慢）时音频不被堆积。这就是 SPEC 里"网关买的是规模和隔离，不是延迟"的落地含义。

## 7. 那 RTMP 又是什么（Month 2 预告）

现在浏览器→网关走 WebSocket（HTTP 升级而来，文本/二进制消息）。RTMP 是另一种**传输协议**：TCP 上的多媒体专用协议，把音视频切成 Message 传输，带时间戳/流 ID，专为推流设计（OBS 推直播都用它）。

对本项目：把"浏览器采集 → WS 上行"换成"采集端 → RTMP 推流"，网关入口多一种协议解析器（tcp/handshake/chunk/stream 四个模块），但**网关内部到 worker 的 gRPC 契约一字不改**——这就是 SPEC 决策 D1"服务拆分"买到的变化隔离。

## 8. 术语速查

| 术语 | 一句话解释 |
|------|-----------|
| PCM | 未压缩的原始采样字节，音频的"BMP" |
| 采样率 16kHz | 每秒 16000 个数值，语音够用 |
| 帧 | 一小段时间（40ms）的音频打包成一次发送 |
| 水位丢帧 | 缓冲超过阈值丢最旧帧，实时流的标准保护策略 |
| seq | 帧的序号，重连后判断从哪续传、是否乱序 |
| AudioWorklet | 浏览器音频采集底层 API，能拿到裸 PCM |
| MediaRecorder | 浏览器便捷录音 API，但输出压缩容器格式 |
| ASR | 语音识别（音频→文字） |
| TTS | 语音合成（文字→音频） |
| VAD | 静音检测，判断"这句话说完了" |
| gRPC bidi stream | 双向持续消息流，两个方向各自独立有序 |
| backpressure | 下游慢导致上游被反压；实时音频系统的做法是丢帧而不是反压 |
